Central and Edge are independently deployable apps in one repository. For deployment with published images, start with the [quickstart](/quickstart). This page covers working on the source.

Open normal development PRs against `main`, titled as Conventional Commits (`feat: …`, `fix: …`, `docs: …`). CI enforces this, and the title decides the next version. See [Releases](/releases#pr-titles-and-versions).

## Repository layout

| Path | Contents |
|---|---|
| `central/` | Central's receiver API, storage logic, and web UI |
| `edge/` | Edge's scanning, encryption, upload, restore, and web UI |
| `shared/go/` | Wire protocol, authentication, HTTP helpers, certificates, hooks, ntfy templates, locks, configuration helpers, and web UI serving |
| `shared/ts/` | Browser scripts and types compiled into both UIs |
| `tests/` | TypeScript tests, grouped by area: `edge/`, `central/`, `shared/` (both UIs), `release/` (release automation), and `ci/` (CI tooling) |
| `deploy-example/central/`, `deploy-example/edge/` | Compose deployments using published images |
| `docs/` | Mintlify documentation |

The root `go.work` joins three Go modules: `central`, `edge`, and `shared/go`. Behavior specific to one app stays in that app's directory. Go also discovers the parent workspace when commands run inside an app directory.

## Build locally

Use the Go version declared in the repository's `go.work` and module files, and **Node.js 24** for the frontend build. From the repository root, install the build tools and generate both UIs:

```sh
npm ci
npm run build
```

Then build an individual server from its app directory:

```sh
cd central
go build ./cmd/server
```

Use `edge` in place of `central` to build Edge.

## Run the tests

CI runs three suites on every PR, and you can run them all locally from the repository root. Go unit tests mock database calls and use in-memory store mocks for service tests. They don't open SQLite databases or connect to PostgreSQL. The Docker end-to-end test starts its own real database.

| Suite | Needs |
|---|---|
| Go unit tests | Go, Node.js 24, and `npm ci` (Go embeds the generated UI) |
| Frontend and release tests | Node.js 24, `npm ci`, and `git` |
| End-to-end test | Docker, `bash`, `curl`, and `jq` |

### Go unit tests

```sh
npm run build
go test ./shared/go/... ./central/... ./edge/...

# One package, filtered by test name
go test ./edge/internal/services/directories/ -run ListChildren -v
```

CI also passes `-race`, which needs a C compiler. On Windows, tests that need symlinks, POSIX permissions, or `sh` report `SKIP`, but CI still runs them.

### Frontend and release tests

```sh
npm test
```

This rebuilds both UIs and runs every `tests/**/*.test.cts` file. Tests are grouped by area:

| Folder | Covers |
|---|---|
| `tests/edge/` | Edge UI, such as the directory tree, file browser, and refresh loop |
| `tests/central/` | Central UI, such as the overview, saved keys, and snapshot decryption |
| `tests/shared/` | Behavior both UIs share |
| `tests/release/` | Release scripts and workflows |
| `tests/ci/` | CI tooling, such as the test report generator |

To run some tests without rebuilding every time, run `npm run build` once (again after TypeScript changes), then:

```sh
node --test tests/edge/directory-tree.test.cts                            # one file
node --test "tests/central/**/*.test.cts"                                 # one area
node --test --test-name-pattern="directory tree" "tests/**/*.test.cts"    # by name
```

Quote globs so Node expands them, not your shell. Name new test files after their feature, end them in `.test.cts`, and put them in their area's folder.

### End-to-end test

`tests/integration/e2e.sh` runs PostgreSQL, Central, and Edge in Docker, takes a backup, and recovers it. Build the images it expects first:

```sh
docker build -t 3to1go-central-validation -f central/Dockerfile .
docker build -t 3to1go-edge-validation -f edge/Dockerfile .
bash tests/integration/e2e.sh
```

It uses host ports `16555` and `16556` and cleans up after itself. On Windows, run it from Git Bash or WSL.

### Test reports

`scripts/test-report.cts` turns results into a single HTML page with pass, fail, and skip counts and each failure's output. `npm test` writes `reports/frontend-tests.html`. For Go tests, convert the `go test -json` output. The coverage page is optional:

```sh
mkdir -p reports && cd edge
go test -json -coverprofile=../reports/edge-coverage.out ./... ../shared/go/... > ../reports/edge-go-tests.json
node ../scripts/test-report.cts go "Edge Go tests" ../reports/edge-go-tests.json ../reports/edge-go-tests.html
go tool cover -html=../reports/edge-coverage.out -o ../reports/edge-coverage.html
```

In CI, each test job writes a summary on its run page and uploads its reports as an artifact, kept for 14 days. Download it from **Artifacts** at the bottom of the run, unzip, and open the HTML file.

| Artifact | Contents |
|---|---|
| `frontend-test-report` | `frontend-tests.html` |
| `edge-test-report`, `central-test-report` | Test report, coverage report, and raw `go test -json` output |
| `e2e-container-logs` | Container logs, only when the end-to-end test fails |

## Repository maintenance

The maintenance workflow checks Go formatting with `gofmt`, scans all three Go modules with `govulncheck`, and runs `npm audit --audit-level=high`, including the frontend build tools. It runs on PRs, pushes to `main` and `prod`, and once a week. The weekly run checks for newly reported vulnerabilities even when the code hasn't changed. Go tests also run the default `go vet` checks.

Dependabot opens weekly update PRs for Go dependencies, npm tools, GitHub Actions, and Dockerfile base images. These PRs use Conventional Commit titles and go through the usual CI and review. Dependabot isn't set up to merge them automatically. See [Dependabot configuration](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference) and [Go vulnerability management](https://go.dev/doc/security/vuln/) for details.

Report vulnerabilities using the repository's [security policy](https://github.com/thesteau/3to1go/blob/main/SECURITY.md).

## Frontend sources and generated files

Edit TypeScript in `central/static/ts`, `edge/static/ts`, or `shared/ts`. Each app compiles the shared scripts along with its own. They're classic scripts that share one global scope per app, so inline HTML handlers can call their functions. Don't add `import` or `export`.

Go embeds the generated `central/static/js` and `edge/static/js`, so generate them before `go build` or `go test` with `npm run build` at the root, or `go generate ./...` in an app folder. They're gitignored. Don't edit or commit them or any other JavaScript (`.js`, `.mjs`, `.cjs`, `.jsx`, or source maps). CI rejects it.

For continuous compilation, use `npm run watch` (Central) or `npm run watch:edge` (Edge), then rebuild and restart the Go server to serve the new assets.

## Build with Docker Compose

`central/docker-compose.yml` and `edge/docker-compose.yml` build from this checkout, using the repository root as build context so shared code is included. Copy the app's `.env.example` to `.env`, configure it as in [Central installation](/central/install) or [Edge installation](/edge/install), then from that app's folder:

```sh
docker compose up -d --build
```

For published images, use `deploy-example/` instead.
